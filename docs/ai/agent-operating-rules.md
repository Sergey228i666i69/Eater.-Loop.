# Правила Работы Агента

## Перед Любым Изменением

1. Выполни `git status --short --branch`.
2. Если ветка `main`, создай рабочую ветку с префиксом `codex/`.
3. Отметь чужие изменения и не трогай их. Особенно осторожно с `.tscn`,
   `project.godot`, `.import`, `.uid`, `addons/` и бинарными ассетами.
4. Читай через `rg`, `rg --files`, `sed`, `find`. Не полагайся на старые
   выводы, если факт дешево перепроверить.

## Правка Файлов

- Ручные изменения делай через `apply_patch`.
- Не делай broad refactor, если задача решается документом, маленьким
  validator-ом или точечной правкой.
- Если меняешь код поведения, обнови связанные docs и focused tests.
- Если меняешь структуру проекта, обнови `structure.txt`, когда это помогает
  следующему агенту не заблудиться.
- Не коммить чужие dirty changes. Stage только свои файлы.

## Когда Можно Менять Код

Код добавляй только если без него документация будет врать или не сможет
сдержать повторение ошибки. Хорошие причины:

- нужен focused validator для нового scene contract;
- старый документ ссылается на несуществующий путь и требуется минимальная
  совместимая правка;
- шаблон контента не отражает правила, которые документация требует от автора.

Плохие причины:

- "по пути" переписать крупный facade;
- переименовать сцены ради вкуса;
- расширить публичный API без теста и реальной потребности.

## Общение С Пользователем

- Если пользователь просит только ответ или анализ без изменений, работай
  read-only.
- Если пользователь просит сделать документацию, ремонт или запуск, выполняй
  задачу до проверенного результата.
- Если упираешься в реальный blocker и пользователь просил не чинить проблемы
  самостоятельно, остановись и сообщи конкретную причину.

## Коммиты

После успешного полного suite создай коммит с понятным названием. Если suite
не запускался или упал, не маскируй это: финальный отчёт должен сказать, что
именно проверено и где риск.
